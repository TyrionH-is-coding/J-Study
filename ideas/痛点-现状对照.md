# 问卷痛点 vs J-Study 现状对照

数据来源：大学生 AI 辅助复习与课件学习资料需求调研（N=40）

---

## 一、已有管线（PDF → 学习资料生成）的自由度缺口

当前管线是单入口单出口的：上传 PDF → 固定检索 + 固定 prompt → 一份 Markdown。用户对输出的控制权几乎为零。

### 1.1 用户需要的「自由度」列举

| 用户需求 | 痛点来源 | 当前状态 | 如何加入已有工作流 |
|---------|---------|---------|------------------|
| **输出风格选择**：速记版 / 详解版 / 刷题版 / 框架版 | Q17：37.5% 需要多风格切换；Q18：考前速记 5% 选为第一功能 | 始终「课件严格模式」，soul.md 定义了模式但从未切换 | prompt 中插入模式选择开关。在 `build_generation_prompt()` 接受一个 `mode` 参数，用不同的 system prompt 引导 LLM 输出不同风格。风格定义可放在 domain pack 的配置 JSON 中 |
| **考试重点突出**：不只总结课件，要指明哪些更容易考 | Q6：70%「不知道哪些更可能考」；Q16：72.5% 需要考试重点整理 | 完全缺失。管线无考试重点推理 | 路径：让用户可选上传往年题/重点标记 → pipeline 增加「重点推理步骤」，在检索后、生成前用 LLM 分析检索结果与重点标注的关联，输出优先级标记（⭐⭐⭐/⭐⭐/⭐）。本质是增加一次 LLM 调用，不改变管线结构 |
| **「重写」vs「总结」控制** | Q6：60%「课件逻辑不清楚，需要重新整理」 | 意图是重写（soul.md），但实际靠一次性 prompt 引导，没有显式控制 | 在 prompt 中增加一条显式指令：「重写模式：重新组织课件结构 / 总结模式：保留课件原始结构仅浓缩」。用户通过 `scenario_id` 或新参数选择 |
| **是否使用 outline** | Q5：45%「老师画重点/复习范围」已在使用 | 已支持 outline 上传，但无 outline 时的行为是走「课件严格模式」（prompt 写死） | 将 prompt 中的模式选择从硬编码改为条件分支。已有 `build_generation_prompt()` 接受 `outline` 参数，但分支逻辑也写死。改为在 domain pack 中定义模式选择规则 |
| **生成内容粒度控制**：整门课 vs 单章 | Q20：2.5%「只按章节使用，不一次上传整门课」 | 只支持单 PDF 输入，无课程级聚合 | 单 PDF 工作流不变。课程级聚合需要新 endpoint：上传多 PDF + 选场景 → 先出目录框架 → 后台按章节逐个生成。这是 pipeline 的编排层变化，不是核心管线变化 |
| **生成内容的选择性**：指定哪部分重要/忽略哪部分 | Q14：37.5%「不知道考试重点」 | 无任何用户前置偏好输入 | 在提交时增加「重点关注」文本框（自由输入或从 outline 自动提取），注入检索 query 和 prompt。不做复杂配置，加一行 prompt 引导即可 |
| **来源标注可见性** | Q14：67.5%「AI 容易编造」 | 证据系统（hidden comments + PDF 跳转）已完整，但用户不可见 | 证据系统本身完整。只需在前端渲染 hidden comments 为可视链接即可（前端问题，非后端缺口） |
| **生成内容导出** | Q22：87.5% 需要导出 Markdown/PDF | 后端存了 .md 文件，但无导出 endpoint | 新增 `/api/jobs/{job_id}/export?format=pdf|md`  endpoint，用 python 库将 markdown 转为 PDF。不改变管线 |

### 1.2 架构上如何加入

已有 pipeline 的设计允许增量改造，不需要重写：

```
当前: PDF → parse → chunk → retrieve → prompt → LLM → output
                                         ↑
                                    硬编码 soul.md + 固定指令

改造后: PDF → parse → chunk → retrieve → prompt → LLM → output
                                                ↑
                                     domain pack (含多种模式定义)
                                     user preference (风格/粒度)
                                     可选额外输入 (重点/往年题)
```

改动集中在 `build_generation_prompt()` 和 `pipeline.run_mvp()` 的参数签名上。`domain pack` 的接口（`medicine.py` 中的 `build_generation_prompt`、`build_study_queries`、`audit_output_quality`）需要扩展以接收用户偏好参数。

**但前提**：当前 `build_study_queries()` 硬编码了 14 条球菌关键词。任何多模式改造之前，需要先让 study queries 可配置或自动生成，否则换课程、换风格时检索层就偏了。

## 二、关键痛点 — 管线未覆盖的缺失功能

以下需求当前管线完全不覆盖，需要新增模块或新服务。

### 2.1 自测题与答案解析

| 问卷数据 | 严重性 |
|---------|-------|
| Q16：57.5% 需要例题/自测题，65% 需要答案解析 | 🔴 高 |
| Q18：22.5% 选「自测题+解析」作为第一版优先功能 | 第二优先 |
| Q11：42.5% 已在用 AI 生成练习题 | 用户已经在做这个事了 |

**为什么管线里没有：**
roadmap 排到了 Phase 6，优先级低。

**建议路径：**
不改变现有总结管线。新增独立的 `POST /api/generate/questions` endpoint：
1. 复用已有的 evidence（从已完成 job 中取）
2. LLM 基于证据生成选择题/简答题
3. 答案必须绑定 evidence ID（复用已有的证据系统）
4. 需要「往年题上传 → 风格提取」作为辅助输入才能生成像该校风格的题

**不要做的事：** 做题生成不需要实时。可以做成异步 job，和总结管线共享同一个 job store。

### 2.2 易混点自动识别与对比

| 问卷数据 | 严重性 |
|---------|-------|
| Q6：27.5%「概念、流程或表格容易混淆」 | 🟡 中 |
| Q16：42.5% 需要易混点对比 | 🟡 中 |

**为什么管线里没有：**
soul.md 提到了表格对比，但没有主动识别易混点的逻辑。

**建议路径：**
在现有 `audit_output_quality()` 步骤后增加一个后处理步骤，或作为一个独立生成任务：
1. 从已生成的 markdown 中提取概念对
2. LLM 判断哪些有混淆可能
3. 生成对比表，同样绑定 evidence
4. 可以作为总结输出的附录，也可以独立 API

### 2.3 记忆口诀自动生成

| 问卷数据 | 严重性 |
|---------|-------|
| Q16：35% 需要记忆口诀 | 🟢 低 |
| Q18：0% 选为第一功能 | 优先级最低 |

**当前关联：**
`mnemonics.md` 有 6 条硬编码口诀，`retrieve_mnemonics()` 做关键词匹配检索。没有生成逻辑。

**建议：** 不做。0% 的人选为第一功能。在自测题和易混点之后考虑。

### 2.4 异步课程级生成 + 进度通知

| 问卷数据 | 严重性 |
|---------|-------|
| Q20：42.5%「希望后台生成后通知」，32.5%「先出框架再逐章生成」 | 🔴 高 |
| Q19：77.5% 可接受 1-3 分钟/章，但需要进度显示 | 🔴 高 |

**为什么管线里没有：**
当前 job 系统是单线程 `BackgroundTasks`，无队列，无 WebSocket 或轮询外的进度推送。

**建议路径：**
这是个架构投入，不是功能投入。分两步：
1. **短期**：`POST /api/generate` 返回 job_id，前端轮询 `/api/jobs/{id}`。已有。只需要前端做进度条
2. **中期**：课程级批量上传需要新 endpoint `POST /api/generate/course`：上传多个 PDF → 后台排队逐个生成 → 完成后通知。需要引入真正的任务队列（Redis +  worker）

**不要做的事：** 单 PDF 场景下不需要改动。课程级场景在 Pilot 阶段不一定出现。

### 2.5 热知识：AI 编造与信任问题

| 问卷数据 | 严重性 |
|---------|-------|
| Q14：67.5%「AI 容易编造或不准确」 | 🔴 核心信任问题 |

**当前状态：**
证据系统（hidden evidence comments + PDF 页面跳转）是解决这个问题的正确架构。但：
- 当前只有后端系统，前端未渲染
- 用户看不到证据 → 等于没有
- 质量审计（`audit_output_quality`）的输出没有暴露给用户

**建议：**
这不是新功能，是现有功能的前端落地。优先级应在第一个前端版本中解决。

### 2.6 当前管线做不了的总结

| 痛点 | 为什么现有管线做不了 | 需要什么 |
|------|--------------------|---------|
| 70%「不知道考什么」 | 管线只知道课件内容，不知道考试倾向 | 往年题/重点标注作为额外输入 |
| 62.5%「内容太多抓不住重点」 | 管线没有优先级区分，对所有 chunk 同等对待 | `audit_output_quality` 之外再加一个「重点标记步骤」 |
| 57.5%「看完记不住」 | 输出是静态 Markdown，没有间隔重复/记忆曲线 | 超出当前产品范围，属于独立工具 |
| 30%「没时间整理笔记」 | 管线已经省去了手动整理时间 | ✅ 已有管线已解决 |
| 30%「英文/术语难理解」 | soul.md 要求首次出现写全称+缩写+中文 | ✅ 已有管线已解决 |

---

## 总结：最应该优先补的三个缺口（不改管线结构）

1. **输出风格选择** — 改 prompt 模板 + 加一个参数即可。投入最小，产出最直接（覆盖 Q17 的 37.5% 需求）
2. **考试重点推理** — 需要额外输入（往年题/重点标注），但现有的 evidence 系统可以复用。投入中等，覆盖 Q6 的 70% 最大痛点
3. **来源可视化** — 证据系统已经是后端最好的那一档，前端渲染即可解决 67.5% 的信任问题
